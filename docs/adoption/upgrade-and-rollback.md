# 升级与回滚

Module、generated projection 和 materialized source 是三个独立状态层。升级和回滚必须分别记录和验证，
不能用整个 Git tree 覆盖业务修改，也不能把版本号当作 generated/source 状态证明。

## 升级前

在隔离 worktree 中记录：

- `go.mod`、`go.sum`、`go.work`、`go.work.sum` 和当前 module resolution；
- consumer binary 的 `version --json` 与 `inspect --json`；
- owner facts、声明的 generated/extensions scopes 和当前 generated bytes；
- 已选择 source 的 Source Lock、target 和当前 local delta。

先升级 module pin，再重新构建 consumer CLI 和读取 inspection。命令或 schema 变化时更新业务执行计划，
不要从旧文档猜测兼容行为。

## Generated projection

从当前 owner facts 直接重新生成。默认规则是：

- consumer 显式声明 generated output scopes 和位于其外的 extensions scopes；
- generator 校验仓库边界、`.git`、路径逃逸、重叠、大小写冲突和 symlink 后，清空并重建 generated 目录；
- extensions 中的 hooks、slots、actions 和业务 logic 不创建、不更新、不删除；
- 生成失败返回非零并允许保留部分变更；consumer 使用 Git diff 审阅，使用 Git restore 恢复；
- 生成结果通过 parse/typecheck/compile 和 consumer test 后，再次生成并要求 Git diff 为空。

Nexa 不维护 generation plan、ownership manifest、staging、自动回滚或自动 merge。升级时始终从当前工作树、
fresh inspection 和当前 owner facts 重新生成，不重放旧 invocation，也不推断历史 ownership。

## Source upgrade

Source upgrade 使用 old provider baseline、consumer local source 和 new provider baseline 形成三方计划。
冲突必须显式返回且不写入冲突候选；clean candidate 在 staging 中通过 manifest recipe 后按文件发布。

Source publish 中途失败时，保留真实错误和已经完成的普通文件状态。下一次从当前 repository 和 Source Lock
重新 plan；不使用 transaction log、自动 Recover 或并发锁恢复旧过程。

## 分层回滚

| 层 | 恢复输入 | 验证 |
| --- | --- | --- |
| Module | 升级前 module/workspace 文件 | `go mod verify`、重新构建与 fresh inspection |
| Generated | 当前 owner facts 和 Git checkpoint | fresh direct generation、重复生成无 diff、parse/typecheck/compile |
| Source | 明确保存的 source checkpoint 和 Source Lock | fresh source plan、直接生成、consumer build/test |

Module rollback 不自动恢复 generated/source；generated rollback 不运行旧 generator；source rollback 不覆盖
consumer 未纳入 checkpoint 的修改。数据库、部署和远端 runtime 由 consumer ops 的独立 checkpoint 处理。

完成任何升级或回滚后，重新执行[采用验证矩阵](verification-matrix.md)。
