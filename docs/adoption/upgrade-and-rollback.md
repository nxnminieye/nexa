# 升级与回滚

升级和回滚只消费 typed final-state checkpoint。精确 module lock、consumer-authored facts、Artifact Manifest/generated bytes，以及被选择时的 Source Lock/source snapshot，分别证明不同层的状态；任何一层都不能替代另一层。

## Module 切换保护

- 采用前记录并保护 consumer 原有的 `go.mod`、`go.sum`、`go.work` 和 `go.work.sum`；不得把临时采用配置混入其他业务改动。
- 本地 module replace 或临时 `go.work` 必须明确指向预期框架目录，并在验证后恢复 consumer 原有 module/workspace 状态。
- Source Bundle 使用 exact release、profile、provider identity、manifest/tree digest 和 canonical Source Lock；目录名或 capability presence 不能替代这些 identity。
- Artifact/API/Service Manifest 必须由当前 typed owner facts 重算 SourceRef、Digest、generator identity 和 artifact bytes。Module 版本相同不代表 projection 相同。
- Inspection 与已审核任务计划不一致时停止执行，更新计划并重新审核；不得从 help、文档或历史命令恢复执行。

升级前可以无条件读取：

```bash
nexactl inspect --json
nexactl version --json
```

任何后续 nonbuiltin plan、check 或 write 都必须由当前已审核任务计划明确列出，并在 fresh inspection 中核对 command path、owner、flags、schema 和副作用。Repository write 前重新确认输入和 affected files。

## 持续升级规则

1. 记录当前 module/workspace 状态、inspection、typed facts、manifests、generated bytes，以及适用的 Source Lock/source tree digest。
2. 在隔离 worktree 中用本地 replace 或临时 `go.work` 指向待验证框架目录，不改变业务仓原有 module/workspace 状态。
3. 对受控生成执行只读重建和 drift/ownership 检查；只有 accepted plan digest、source snapshot 与 ownership probe 仍一致时才写入。
4. 对已选择 Source Bundle 使用 old base、local、new base 三方计划。双方冲突时零写入；clean merge 在
   invocation staging 中通过 validation，逐文件发布完成且最终 target digest 通过后才推进 Source ownership snapshot。
5. 最后分别验证 module graph/build info、manifest/source closure、generated parse/typecheck/compile、consumer build/test 和实际运行行为。

## 四层回滚

| 层 | Checkpoint | 允许恢复的内容 | 独立验证 | Framework 验证责任 |
| --- | --- | --- | --- | --- |
| Module | 切换前记录的 `go.mod`、`go.sum`、`go.work`、`go.work.sum` 与 inspection | 只恢复 module/workspace 选择 | 文件恢复、`go mod verify`、fresh inspection；facts/generated/source 不变 | 必须独立验证 |
| Generated projection | 当前 typed owner facts、Artifact Manifest 与 generated byte digest | 只恢复 manifest 闭包中可证明归属的 generated artifact | source/manifest/digest 重算、ownership probe、parse/typecheck/compile；module/facts/source 不变 | 必须独立验证 |
| Source Bundle source | typed Source ownership snapshot、old/local/new source snapshot 与 closed inventory | consumer 按本地 checkpoint 明确恢复 authoring/source files，再生成 fresh plan；框架不自动重放或回滚旧 invocation | exact source/ownership digest、fresh plan、generation check、consumer build/test；未选择时证明 `not-applicable` | 选择时必须验证；否则 `not-applicable` |
| Runtime/deployment | consumer ops 自己批准的数据库、集群和远端运行时 checkpoint | 仅由 consumer ops 的独立流程处理 | 对应运行环境的人工 gate、部署与数据验证 | `not-verified-by-framework` |

Framework adoption 只验证前三层，并保持它们彼此独立。Module rollback 不能恢复 generated artifact 或 materialized source；
generated rollback 不能运行旧 generator 或读取旧事实；Source Bundle rollback 不能用整个 Git tree 覆盖
consumer 修改，也不能假定框架保存了可重放的旧事务。第四层始终留给 consumer ops，不连接共享数据库、
Kubernetes、Argo 或远端运行时。

回滚 controller 不读取 typed checkpoint 之前的 comment marker、parser、converter、generator 或事实副本。只有 checkpoint 中的精确 refs、digests 和 owner manifests 可以成为恢复输入。

首个 RC 明确不选择 runtime `nexa` CLI、Python SDK、Python artifacts 和 HTTP parity。升级与回滚不会写入或探测这些命令路径，也不会把它们计入已验证层。
